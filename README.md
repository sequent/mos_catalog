# Поиск аналогов материалов и оборудования

Прототип поиска аналогов по смыслу и по техническим характеристикам из названия позиции. Пользователь вводит наименование своими словами; система показывает до 5 позиций из базы (2381 строка): с ценой, оценкой, сравнением характеристик запроса и позиции и вердиктом. Если подходящей позиции нет, система говорит «не найдено», а не показывает случайные строки.

Главный документ: [ARCHITECTURE.md](ARCHITECTURE.md): схема поиска (три листа), описание шагов простым языком, что делает код, модель и человек, проверка качества, ограничения и план.

## 1. Как запустить

### 1.1 Одной командой (Docker): так разворачивается демо

```bash
docker compose up --build
```

Страница: **http://localhost:8765**. Документация API: `/docs`. Состояние: `curl http://localhost:8765/health`.

- **Порт.** Снаружи 8765 (внутри контейнера сервис слушает 8000); сменить: `APP_PORT=80 docker compose up --build -d`.
- **Сборка.** Нужен интернет и Docker (проверено на Docker 29.9.2, Linux arm64). При сборке скачивается модель `multilingual-e5-small` (≈470 МБ), обрабатывается база и считаются эмбеддинги; первая сборка занимает несколько минут, образ ≈ 1,3 ГБ.
- **Работа.** Контейнер стартует за секунды, не требует интернета и работает без прав администратора; `restart: unless-stopped`; состояние сервиса проверяет `HEALTHCHECK` (`/health`).
- **Правки.** Файлы `config/rules.yaml` (правила) и `config/dictionaries.yaml` (словарь) читаются при сборке: после правки снова `docker compose up --build` (правила пересобираются за секунды, словарь ≈ 1 минута). Горячей перезагрузки нет.

```bash
curl -s -X POST http://localhost:8765/search -H 'Content-Type: application/json' -d '{"query": "ворота откатные 6000х2250", "limit": 5}'
```

Ответ: `status` (`found` только при подтверждённой позиции), `display_status` и `status_line` (что написать на экране), `table` (не больше `limit`, от 1 до 5: подтверждённые первыми, затем «требует проверки»), у каждой позиции `name`, `price`, `verdict`, `needs_review`, `score` и `score_parts`, `comparison` (характеристики запроса и позиции: совпало / отличается / нет данных; у каждой строки `evidence` с источником, фрагментом и координатами в нормализованном тексте), `candidate_extra_attributes` (что позиция называет сверх запроса), `candidate_unparsed_constraints` (что в названии позиции не удалось разобрать) и `explanation`; также `nearest_rejected`, `query` (как система поняла запрос и какие допущения приняты), `rules_version`, `diagnostics`.

**Проверка запущенного сервиса** (23 проверки: страница, подтверждённая позиция, замена по правилу, вариант «к проверке», «не найдено», лимит, ошибки 422 и сравнение 10 запросов со снимком ответов):

```bash
python3 scripts/smoke_test.py --base-url http://localhost:8765
```

Полная проверка чистого запуска (копия репозитория, сборка, ожидание `healthy`, проверка с хоста и из образа **без сети**): `scripts/clean_run_check.sh`. Сборка требует сети (PyPI, Hugging Face); другая ОС и сборка без сети не проверялись.

### 1.2 Без Docker (разработка)

Нужен Python 3.12. Окружение без `torch` (хватает ONNX Runtime):

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python -I scripts/download_model.py      # модель в models/ (≈470 МБ, в репозитории её нет)
.venv/bin/python -I scripts/prepare_catalog.py     # обработка базы → data/processed/
.venv/bin/python -I scripts/build_index.py         # эмбеддинги базы → data/index/ (≈15 с на CPU)
.venv/bin/python -I -m uvicorn --app-dir pipeline analog_search.api:app --port 8765
```

Тесты (959 штук: нормализатор, извлечение, типы, правила и их валидация, сравнение, вердикт, лимит, манифесты, API и страница, схема, замер, реестр допущений):

```bash
.venv/bin/python -I -m pytest -q -p no:cacheprovider
```

Инструменты:

```bash
.venv/bin/python -I scripts/search_cli.py "кабель КВВГнг-LS 7*1.5" --debug   # полный ответ схемы в консоли; --debug: сравнение по каждой характеристике
.venv/bin/python -I scripts/explain.py "кабель КВВГнг-LS 7*1.5"             # как система понимает любой текст: тип, характеристики, пометки
.venv/bin/python -I scripts/batch_search.py ведомость.xlsx --column "Позиция"            # список позиций (xlsx, csv, txt) через всю схему, результат в CSV (состояние входной ячейки `input_state`, статус, первая строка таблицы, а для не подтверждённой строки ещё ближайшая отклонённая позиция и причина отказа: `nearest_rejected_name`, `nearest_rejected_why`); битая строка не останавливает прогон. В контейнере писать в `/app` нельзя: указывайте `--out /tmp/result.csv`
.venv/bin/python -I eval/evaluate.py --run-id my-run                        # проверка качества на 40 контрольных запросах (отчёт в reports/quality/runs/my-run/)
```

**Как применить изменение.** Правила (`config/rules.yaml`): проверить примеры (`pytest tests/test_rules.py tests/test_rules_validation.py`) и перезапустить процесс; индекс не пересчитывается. Словарь, код извлечения или xlsx: `prepare_catalog.py` → `build_index.py` → перезапуск (иначе сервис не стартует: манифест каталога не совпадёт, и сообщение назовёт команду). Модель: `download_model.py` → `build_index.py` → перезапуск. Сервер никогда не пересчитывает индекс сам.

**Схема** (`docs/scheme*.svg`, `docs/scheme.drawio`) генерируется из одного описания: `python scripts/build_scheme.py --overwrite`; тест сверяет файлы с описанием и с кодом.

## 3. Допущения

Предметную область автор не знает. Всё ниже: допущение автора, которое должен подтвердить или поправить специалист заказчика. Столбец «Где менять» показывает, где это записано. «Кому» = кто решает: **С** — специалист, **Р** — руководитель проекта.

### 3.1 Данные

| № | Допущение | Где менять | Кому |
|---|---|---|---|
| Д1 | Источник: исходный `.xlsx`. TSV идентичен построчно (проверено), цены в нём лишь выведены с запятыми. | — | — |
| Д2 | Цена показывается как есть и **не участвует** в отборе и ранжировании (в задании: «цена условная»). | `rules.yaml` → `policy.ranking` | Р |
| Д3 | Каждая строка — отдельная закупка. Дубликаты (3 строки, различаются регистром бренда) не удаляются. | — | Р |
| Д4 | Названия объектов «Объект-А», «ГЭС-1» и т. п. (45 строк) не несут технического смысла и убираются из текста поиска; в показе остаются. | код (`normalize.py`) | — |

### 3.2 Нормализация и характеристики

| № | Допущение | Где менять | Кому |
|---|---|---|---|
| Н1 | `х`, `x`, `×`, `*`, `Х`, `X` между цифрами означают умножение; запятая между цифрами — десятичная. Точка в кодах (`221.04-1`, `ШК-FA.4`) десятичной не считается. | код | — |
| Н2 | «Мп», «Мпикс», «MP» после числа — мегапиксели. «МПа» — давление, не разрешение. | код | — |
| Н3 | Кириллические буквы, похожие на латинские (А В Е К М Н О Р С Т Х У), в кодах моделей при сравнении считаются латинскими; `l` и `I` — одной буквой. В показе остаётся оригинал. | код | С |
| Н4 | «В» после числа — вольты, кроме случая «2 В комплекте» (за «В» через пробел идёт слово). | код | — |
| Н5 | «25 мм» без слова «диаметр» у труб, трубок и рукавов означает **диаметр**. Для остальных типов остаётся «просто мм». | `dictionaries.yaml` → `bare_mm_means` | **С** |
| Н6 | Числа в «(прим. …)» и «(или аналог)» относятся к альтернативной позиции и **не участвуют** в строгом сравнении. | код | **С** |
| Н7 | `Ду`/`DN` — **условный проход**, это отдельная характеристика, не наружный диаметр. Допустимы только значения стандартного ряда (иначе `DN1201` — код изделия). | код (`attributes.py`) | **С** |
| Н8 | Единицы приводятся к: мм, В, А, кВт, кВА, МПа, Мп, кг. Т = 1000 кг, кВ = 1000 В. | код | — |
| Н9 | Кабель: буква `Э` в маркировке (до «нг») — экранированный; `LS`, `FRLS`, `HF` — класс пожарной безопасности; число после сечения (`-1000`) — номинальное напряжение; суффиксы `ок/мк/мс` — форма жилы. | код | **С** |
| Н10 | Размеры хранятся «как написано» и отсортированными. Важен ли порядок, решает правило типа (п. П6). | `rules.yaml` → `dims_order` | **С** |
| Н11 | Параметры внутри кодов моделей (например, 12 В в `SKAT-V.12DC-18`) не извлекаются. | — (ограничение) | С |

### 3.3 Тип изделия

| № | Допущение | Где менять | Кому |
|---|---|---|---|
| Т1 | Тип определяется по началу названия по словарю (~210 записей) и опознан у 86 % строк. 14 % без типа: **это нормально**, такие позиции ищутся по словам, смыслу и характеристикам. | `dictionaries.yaml` → `types` | **С** |
| Т2 | Тип — **сигнал, а не фильтр**: он никого не отсеивает до проверки характеристик. | `rules.yaml` → `policy.type` | **С** |
| Т3 | Тип бывает конкретный (многословный или из списка `specific_single_word_types`: «кабель контрольный», «видеокамера») и общий («шкаф», «блок», «комплект»). Конфликт типов возможен только между двумя конкретными типами из разных семейств. | `dictionaries.yaml` | **С** |
| Т4 | Семейство типа = первое слово его названия («кабель контрольный» → «кабель»). | — | С |

### 3.4 Услуги, надбавки, комплекты

| № | Допущение | Где менять | Кому |
|---|---|---|---|
| У1 | Перевозка, погрузка, разгрузка (90 строк) и надбавки/доплаты (14) — **отдельный пул**: запрос про услугу ищет только среди них, остальные запросы их не видят. | `rules.yaml` → `policy.services` | Р |

### 3.5 Правила замен (все — черновик автора)

| № | Допущение | Где менять | Кому |
|---|---|---|---|
| П1 | Число жил и сечение кабеля совпадают **строго**. | `rules.yaml` → `cable_cores_section` | **С** |
| П2 | Экран кабеля (`Э`): отличие **показывается, но не отклоняет**: итог «проверить». Следствие для примера из задания: запрос «КВВГнг-LS 7*1.5» даёт «не найдено» + кандидат `КВВГЭнг(A)-LS 7х1,5` в списке «не подтверждены». Если `Э` не важна, правило переводится в `ignore`. **Решение автора прототипа: оставить `flag`**, пока специалист не подтвердил обратное; на защите это объясняется как осторожное умолчание. | `rules.yaml` → `cable_screen` | **С** |
| П3 | Класс пожарной безопасности (`LS` / `FRLS` / `HF`) совпадает строго. | `rules.yaml` → `cable_fire_class` | **С** |
| П4 | Разрешение камеры: допустимо отличие на **одну ступень** шкалы 1–2–3–4–5–8–12 Мп. Шкала взята как правдоподобная, не из методики. | `rules.yaml` → `camera_resolution` | **С** |
| П5 | Размеры ворот совпадают строго, порядок сторон не важен. | `rules.yaml` → `gate_size` | **С** |
| П6 | Порядок сторон: у ворот не важен (`sorted`), у лотка, воздуховода и жалюзийной решётки важен (`ordered`). Для остальных типов поведение задаёт `defaults.dims_order_unlisted`: `check` (по умолчанию) — совпадение только после перестановки = «проверить», `sorted` — порядок не важен, `ordered` — важен. На пробном наборе от этого зависит около 14 % запросов с размерами. | `rules.yaml` → `dims_order`, `defaults.dims_order_unlisted` | **С** |
| П7 | Для характеристик без правила любое числовое отличие — **конфликт** (осторожное умолчание). | `rules.yaml` → `defaults` | **С** |

### 3.6 Вердикт, порядок, «не найдено»

| № | Допущение | Где менять | Кому |
|---|---|---|---|
| В1 | Совместимость (B4), ранжирование (B5) и вердикт (B6) — **три разных шага**. Баллы порядка не меняют совместимость. | `rules.yaml` → `policy` | Р |
| В2 | Класс «совместим» возможен только при хотя бы одной подтверждённой характеристике (совпавшей или заменяемой по правилу), совпавшем **надёжном** коде модели или дословно совпавшем названии. **Совпадение типа само по себе не подтверждает**: все камеры не «та же позиция» для запроса «камера». Совпадение «исполнения» (уличный/внутренний) тоже не считается подтверждением. | `rules.yaml` → `policy.evidence` | С |
| В3 | Если подтверждённо подходящих («та же позиция», «допустимая замена») нет, ответ: **«не найдено»**. Слабые кандидаты на это не влияют. | `rules.yaml` → `policy.not_found` | **Р** |
| В4 | Под «не найдено» отдельно показываются до 3 кандидатов «не подтверждены, нужна проверка» и ближайшая позиция с причиной отказа. Это не результат поиска. | `rules.yaml` → `policy.not_found` | **Р** |
| В6 | **Материал** («ПВХ», «сталь», «медь»…) — характеристика по словарю `materials`: другой материал — конфликт, не названный — «нет данных»; ПНД и ПЭ — один материал. Остальные слова запроса, которых не объясняет ни одна характеристика, проверяются покрытием слов: если в названии кандидата меньше 50 % таких слов (синонимы засчитываются), кандидат не может быть «подтверждён». Порог — допущение (был 70 %, но он бракует описательные слова естественных запросов). | `rules.yaml` → `policy.word_coverage`; `dictionaries.yaml` → `materials` | С |

| Разрешение камеры: ±1 ступень | `rules.yaml`, правило `camera_resolution`, `ladder` + `max_steps: 1` | 3 Мп ↔ 2 Мп, 4 Мп: «допустимая замена»; 4 Мп ↔ 2 Мп: конфликт. **Ступень берётся по шкале 1–2–3–4–5–8–12, а не «±1 Мп»:** 5 Мп ↔ 8 Мп тоже замена | `max_steps`, шкала `ladder` |
| Инфракрасный термометр любого производителя | `dictionaries.yaml`: тип «термометр инфракрасный» (в него входит «пирометр») и фраза «любого производителя»; `rules.yaml`: `policy.evidence.confirm_by_type` | Фраза вырезается из запроса, в ответе пишется «принято допущение: производитель не важен». Для типов из списка `confirm_by_type` достаточно совпадения типа, чтобы дать «та же позиция»: у запроса нет других характеристик. Если названа характеристика и она отличается (500 °C против 1000 °C), позиция отклоняется | убрать тип из `confirm_by_type`: тогда «не найдено» |
| Тройник 25×30 мм, любой цвет | `dictionaries.yaml`: цвета и фраза «любой цвет»; `rules.yaml`: `defaults.per_attribute.color` | Цвет теперь характеристика. Без слов «любой цвет»: другой цвет даёт «проверить» (не отклоняет), цвет не названный в базе даёт «нет данных». С фразой «любой цвет» цвет не сравнивается. Размер решает всегда. Цвет сам по себе не доказательство (`weak_attributes`) | `color: exact` (другой цвет отклоняет), `ignore` (цвет не учитывается никогда) |

| «Металлическая» = стальная | `dictionaries.yaml`: материал «металл» и `generic_materials` | «стальная дверь» подтверждается «металлической» (и наоборот). С другими металлами общее слово не конфликтует: «алюминиевая труба» против «металлической» даёт «нет данных» → «проверить», а не «не подходит». С неметаллами (ПВХ, полиэтилен) конфликт. Нержавеющая сталь считается сталью | удалить запись `металл` из `generic_materials`: «металл» станет отдельным материалом, и «сталь» ему не равна |

| Синонимы типов и слов | `dictionaries.yaml`: `synonyms.replace`, тип «клапан противопожарный» | «датчик пожарный/охранный/дымовой» → «извещатель» (**«датчик температуры» остаётся датчиком**); «огнезадерживающий» → «противопожарный» (тип «клапан противопожарный» найден и при обратном порядке слов); «дооснащение» → «доукомплектация»; «действующих» → «существующих»; «Хуавей» → «Huawei». Применяются и к базе, и к запросу | удалить строку из `synonyms.replace` и пересобрать каталог (`prepare_catalog.py`, `build_index.py`) |

Что важно знать. (1) Производитель в системе **не характеристика**: нет словаря производителей, поэтому «любого производителя» просто снимает эти слова с запроса; код модели (`Fluke 561`) остаётся справочным и ничего не блокирует. (2) `confirm_by_type` подтверждает по одному типу: у этого типа в базе одна позиция, диапазон температур и точность в названии не указаны. Для боевых правил специалисту нужно добавить характеристики (диапазон) и решить, чем отличаются приборы. (3) До этого изменения запрос «тройник 25×30 красный» возвращал белый тройник как «та же позиция»: цвет молча игнорировался. Теперь это «проверить».

### 4.2 Как читать выдачу

| Вердикт | Что значит | Что делать |
|---|---|---|
| **Та же позиция** | все названные в запросе характеристики совпали | можно брать |
| **Допустимая замена** | есть отличия, но все разрешены правилами (указано, какими) | проверить, что правило вам подходит |
| **Проверить** | конфликтов нет, но что-то неизвестно (в названии кандидата нет характеристики, это комплект, тип иной, порядок сторон не подтверждён) | решаете вы; такие кандидаты показываются отдельно |
| **Не подходит** | есть конфликт (например, другое сечение) | в выдачу не попадает; видно как «ближайшее» с причиной |
| **Не найдено** | подтверждённо подходящих нет | см. список «не подтверждены» ниже |

Для каждой характеристики видно: **совпало**, **совпало с точностью до порядка**, **допустимая замена**, **конфликт**, **нет данных**.

### 4.3 Как изменить правило

Правила лежат в `config/rules.yaml`. Пример:

```yaml
- id: camera_resolution
  title: "Разрешение камеры: допустимо отличие на одну ступень шкалы"
  applies_to: [видеокамера]       # к каким типам изделий относится
  attribute: resolution_mp        # какая характеристика
  mode: ladder                    # режим сравнения
  ladder: [1, 2, 3, 4, 5, 8, 12]  # шкала ступеней, Мп
  max_steps: 1                    # допустимо отличие на одну ступень
  examples:                       # примеры «да/нет», которые проверяются автоматически
    - {query: "камера 3 Мп", candidate: "видеокамера 2Мп", expect: substitute}
    - {query: "камера 4 Мп", candidate: "видеокамера 2Мп", expect: conflict}
```

Режимы (`mode`):

| Режим | Значит |
|---|---|
| `exact` | значения должны совпасть, иначе конфликт |
| `ladder` | значения — ступени шкалы; отличие не больше `max_steps` — допустимая замена |
| `min_ge` | значение кандидата не меньше запрошенного |
| `flag` | отличие показывается, но кандидат не отклоняется (итог «проверить») |
| `ignore` | характеристику не сравнивать |

Порядок действий:
1. Измените значение в файле (например, `max_steps: 1` → `2`).
2. Обновите пример в `examples`, чтобы он отражал новое решение (если после правки «камера 4 Мп» заменяет «2Мп», ожидание меняется на `substitute`).
3. Увеличьте `version` и смените `status` на `approved_by_specialist`, когда правила утверждены.
4. Запустите проверку: `.venv/bin/python -I -m pytest tests/test_rules.py`. Каждый пример из `examples` правила проверяется автоматически командой `.venv/bin/python -I -m pytest tests/test_rules.py`: после правки он должен проходить (или ожидание в примере нужно обновить).

Правило применяется ко **всем** позициям указанного типа, пересчитывать индекс не нужно. Код менять не нужно.

### 4.4 Как добавить синоним или тип изделия

Файл `config/dictionaries.yaml`.

**Синоним-расшифровка** (заменяет сокращение и в базе, и в запросе):

```yaml
synonyms:
  replace:
    - {pattern: '\bибп\b', to: 'источник бесперебойного питания'}
```

**Синоним-добавка** (слово остаётся, добавляется синоним):

```yaml
  expand:
    - {pattern: 'вариофокальн\w*', add: 'моторизированный объектив'}
```

**Тип изделия** (порядок важен: частное выше общего):

```yaml
types:
  - {name: кабель контрольный, pattern: 'кабел(?:ь|и|я|ю)\s+контрольн'}
```

Шаблоны пишутся в нижнем регистре, `ё` заменяется на `е`. Если вам неудобны шаблоны, пришлите разработчику список «название → тип».

Как проверить: `.venv/bin/python -I scripts/explain.py "текст позиции"` покажет, какой тип и какие характеристики система увидела. Списки для расширения словаря: `reports/extraction/unknown_type.csv` (позиции без типа) и `reports/extraction/uncovered_numbers.csv` (числа, которые никакая характеристика не объяснила).

Тип: конкретный или общий. Однословный тип считается конкретным только если он в списке `specific_single_word_types`. Конкретный тип может дать конфликт («не подходит»), общий только понижает уверенность.

### 4.5 Что НЕ делает подтверждение

Когда вы подтверждаете или отклоняете найденную пару, система запоминает её, и эта пара чуть выше или ниже в выдаче по тому же запросу. **Правила, словари, совместимость и вердикты от этого не меняются.** Если вы замечаете повторяющуюся ситуацию («сечение 1,5 вместо 1 мы всегда принимаем»), система предложит правило, но оно вступит в силу только после вашего утверждения и выхода новой версии `rules.yaml`.

### 4.6 Если выдача неверна

Сообщите разработчику запрос и позицию. Определить, на каком шаге ошибка, помогает таблица «Где логика может сломаться» в [ARCHITECTURE.md](ARCHITECTURE.md#9-где-логика-может-сломаться-и-как-это-обнаружить): характеристика не извлечена, неверный тип, строгое или слабое правило, позиции нет среди кандидатов.

**Что не готово или не гарантировано**

- Не реализованы подтверждения специалиста (B8), журнал и очередь предложений правил, разбор остатка через ИИ (A4+): описаны в ARCHITECTURE.md и отмечены пунктиром на схеме. Страница не хранит историю запросов, нет входа и ролей (прототип).
- **Правила замен, словарь и пороги придуманы автором** (реестр `config/assumptions.yaml`, раздел 3.10); специалист заказчика их не утверждал. Методику замен задаёт заказчик.
- Система осторожна: неизвестная характеристика не подтверждается. Поэтому часть запросов остаётся «требует проверки», а не «найдено». Решение автора по экрану: подтверждённые строки идут первыми, затем «требует проверки» (настройка `policy.ui`).
- Характеристики берутся из названия: параметры вне названия система не видит; в кодах моделей параметры не извлекаются (`SKAT-V.12DC-18` → 12 В); числа из «(прим. …)» в сравнении не участвуют.
- Полнота разбора не гарантирована: числовой guard не ловит все словесные требования; нераспознанное свойство может потеряться (но неразобранное число с единицей не даёт подтверждения).
- Материал, класс, число клавиш, технология печати и ряд других признаков учитываются; цвет, назначение и «рабочий/запасной» проверяет только покрытие слов запроса.
- Типы грубые (семейство «шкаф» — 182 разных изделия); словарь типов и признаков покрывает базу частично и должен расширяться специалистом.
- Модель E5 на контрольных запросах преимущества не показала (цепочка без неё даёт те же результаты); её роль остаётся гипотезой для запросов с перефразировкой.
- Масштаб: нагрузочный замер на 50 тыс. и 500 тыс. строк не проводился; описание и риски в ARCHITECTURE.md, раздел 10.
- Сборка образа требует сети; сборка без сети, другая ОС и архитектура не проверялись.
